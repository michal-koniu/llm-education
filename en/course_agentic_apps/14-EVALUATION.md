**Level:** ⭐⭐⭐⭐ · **Time:** ~5 h · **Requires:** parts 3 (harness), 13 (fleet)

## 0. A number that should change your priorities

> **An agent's score changes more with the harness than with the model.** The same model
> under two scaffolds produces significantly different numbers. The harness decides how
> tools are exposed, how errors are shown and how many attempts the agent gets. **The prompt
> and the planning loop can add or subtract points before the model even starts working.**
> — [Prefactor, Agent Benchmarks](https://prefactor.tech/learn/agent-benchmarks)

Two consequences, both practical:

1. **Other people's model benchmarks tell you nothing** about how the model will behave in
   your system. They were measured under a different harness.
2. **You have to measure your own system**, because otherwise you do not know whether the
   change you just made helped or hurt.

⭐ **This is the part without which all the previous ones are guesswork.** Every "threshold",
"limit" and "variant" from parts 4–13 rests on a measurement. Here you build the machine that
performs it.

## 1. Four levels of evaluation

Most people measure only level 1 and are surprised that the agent is unreliable.

| Level | What it measures | Example | Difficulty |
| :-- | :-- | :-- | :-- |
| **1 · result** | whether the answer is correct | "42 invoices" = true? | ⭐ easy |
| **2 · trajectory** | whether the path to the result made sense | 3 steps or 19? the right tools? | medium |
| **3 · reliability** | whether it works **every time** | 10 runs, how many successes | medium |
| **4 · robustness** | whether it cannot be fooled | injection, edge-case data | hard |

⭐ **Level 3 is the one that separates a demo from a system.** An agent that passes a task
in 7 out of 10 runs **does not work 70% of the time** — it **does not work**, because you do
not know which run you will get.

### 1.1 · `pass^k` — a measure worth knowing

```
pass@k  = did it succeed at least once in k attempts     ← a measure of CAPABILITY
pass^k  = did it succeed in ALL k attempts               ← ⭐ a measure of RELIABILITY
```

An agent with an 80% success rate per step has `pass^5` = 0.8⁵ = **33%**. That means that in
two thirds of cases a series of five tasks will fail at least once.

⭐ **Report `pass^k`, not `pass@k`.** `pass@k` is a number for presentations. `pass^k`
is the number you make decisions on.

## 2. The golden set

### 2.1 · Construction

**A hundred questions is a good target. Fifty is enough to start. Twenty is too few
to detect a 5-point change.**

```json
{
  "id": "Z041",
  "kategoria": "wyszukanie_z_cytatem",
  "pytanie": "What is the payment due date of invoice FV/017/03/2026?",
  "oczekiwane": {
    "zawiera": ["2026-04-14"],
    "nie_zawiera": ["I don't know", "I did not find"],
    "wymaga_cytatu": true,
    "zrodlo": "faktury/2026/03/f017.txt"
  },
  "trajektoria": {
    "max_krokow": 4,
    "wymagane_narzedzia": ["znajdz_dokumenty"],
    "zakazane_narzedzia": ["powloka"]
  },
  "przebiegow": 3
}
```

### 2.2 · Five categories — and why these in particular

| Category | Share | What it guards |
| :-- | --: | :-- |
| **Lookup with a citation** | 30% | basic competence |
| **Synthesis from multiple sources** | 25% | ⭐ this is where context breaks down (part 4) |
| **⭐ Correct refusal** | 20% | questions for which there is **no** answer in the data |
| **Multi-step** | 15% | ⭐ this is where the value of the harness shows (part 3) |
| **⭐ Robustness** | 10% | injections, contradictory data, edge cases |

⭐ **Twenty percent for correct refusal is not excessive.** An agent that always answers
something is **worse than no agent**, because it sounds credible. Without this category in
the set you will be optimizing toward self-confidence, not truthfulness.

### 2.3 · Where to get the questions

| Source | Quality | Note |
| :-- | :-- | :-- |
| ⭐ **Your real sessions from the log** | highest | they are real; you have had them since part 2 |
| ⭐ **Failures that hurt you** | highest | every failure → a new question, forever |
| Model-generated from the corpus | medium | ⚠️ cheap, but they measure what the model thinks is important |
| Invented by hand | variable | usually too easy |

```bash
# Pull candidates from your own logs — the best source you have
python3 testy/z_dziennika.py --ostatnie 200 --tylko-udane > kandydaci.jsonl
```

⚠️ **Never put into the golden set an answer generated by the same model you are testing
without checking it by hand.** You will build a benchmark that measures repeatability, not
correctness.

## 3. Trajectory evaluation

A correct result, an absurd path — this is a real state of affairs and you need to see it.

```python
# $OSA/ewaluacja/trajektoria.py
def ocen_trajektorie(zdarzenia: list, oczekiwana: dict) -> dict:
    krokow = sum(1 for z in zdarzenia if z["typ"] == "narzedzie.wywolanie")
    uzyte  = [z["narzedzie"] for z in zdarzenia if z["typ"] == "narzedzie.wywolanie"]
    bledy  = sum(1 for z in zdarzenia if z["typ"] == "narzedzie.wynik" and z.get("kod"))

    # repeats of identical calls = going in circles
    podpisy = [f'{z["narzedzie"]}:{json.dumps(z["argumenty"], sort_keys=True)}'
               for z in zdarzenia if z["typ"] == "narzedzie.wywolanie"]
    powtorzen = len(podpisy) - len(set(podpisy))

    uwagi = []
    if krokow > oczekiwana["max_krokow"]:
        uwagi.append(f"too many steps: {krokow} > {oczekiwana['max_krokow']}")
    if powtorzen:
        uwagi.append(f"{powtorzen} repeated calls (going in circles)")
    for n in oczekiwana.get("zakazane_narzedzia", []):
        if n in uzyte:
            uwagi.append(f"⚠️ forbidden '{n}' was used")
    for n in oczekiwana.get("wymagane_narzedzia", []):
        if n not in uzyte:
            uwagi.append(f"required '{n}' was not used")

    return {"krokow": krokow, "bledow": bledy, "powtorzen": powtorzen,
            "narzedzia": uzyte, "uwagi": uwagi, "czysta": not uwagi}
```

⭐ **`powtorzen` is the cheapest and most effective pathology detector.** An agent
calling the same thing twice with the same arguments is **definitely** not making progress.
It is the same signal as the state fingerprint from part 3, only cheaper to compute.

## 4. The judge — and why it cannot be the same agent

### 4.1 · The self-verification problem

> When sampling trajectories, self-reflection is prone to **self-verification
> bias**: the agent evaluates its own intermediate results **from the same trajectory
> state that produced them**. This coupling interweaves verification
> with self-justification and leads to accepting flawed results.
> — [arXiv 2603.02798](https://arxiv.org/pdf/2603.02798)

Translated into practice: **an agent that got it wrong will not notice, because it looks at
the problem with the same flawed set of assumptions.** Research from ICLR 2024 says the same:
models cannot reliably correct their own reasoning without a signal from outside.

### 4.2 · Four sources of verification, from the strongest

| Source | Strength | Cost | Use |
| :-- | :-- | :-- | :-- |
| ⭐⭐⭐ **Execution** | highest | low | the test passes, the file exists, the sum matches |
| ⭐⭐ **Pattern matching** | high | zero | the quote appears in the source, the format matches |
| ⭐ **A judge in an isolated context** | medium | medium | "is the answer consistent with the document" |
| ✗ **Self-reflection** | **lowest** | low | ⚠️ only as a hint, **never as a gate** |

⭐ **The order is the whole lesson here.** Before you reach for a model judge, check whether
you can verify by execution or by pattern. More than half the questions in a well-built
golden set can be — and these two sources are **free and reliable**.

### 4.3 · A judge in an isolated context

```python
PROMPT_SEDZIEGO = """Assess whether the ANSWER correctly answers the QUESTION
based on the SOURCE.

You have no access to anything beyond what is below. Do not assume context.

Criteria (each separately):
1. CONSISTENCY — do the answer's claims follow from the source? (yes/no/partially)
2. COMPLETENESS — does it answer the whole question? (yes/no/partially)
3. QUOTE — does the quote given appear VERBATIM in the source? (yes/no/no quote)
4. FABRICATED — does it contain claims that are NOT in the source? (yes/no)

Return JSON: {{"zgodnosc":…,"kompletnosc":…,"cytat":…,"wymyslone":…,"uzasadnienie":"…"}}

QUESTION: {pytanie}
SOURCE: {zrodlo}
ANSWER: {odpowiedz}"""

def sedzia(pytanie, zrodlo, odpowiedz, wywolaj_model_sedziego):
    """⭐ The judge DOES NOT SEE: the trajectory, the agent's prompt, the history. Only these three things."""
    return json.loads(wywolaj_model_sedziego(
        [{"rola": "user", "tresc": PROMPT_SEDZIEGO.format(
            pytanie=pytanie, zrodlo=zrodlo, odpowiedz=odpowiedz)}],
        gramatyka=GRAMATYKA_WERDYKTU)["tresc"])
```

**Three rules for the judge:**

1. **An isolated context.** It does not see how the agent arrived at the answer — otherwise
   it can be persuaded by the reasoning instead of the result.
2. **Criteria separately.** "Is this a good answer" yields noise. Four binary questions
   yield signal.
3. **A different model than the one being evaluated**, if you can. `qwen3-32b` evaluates
   `gpt-oss-20b`.

### 4.4 · Calibrating the judge

⚠️ **The judge is a model too and it also makes mistakes. Before you trust it — measure it.**

```bash
# 40 cases that you graded by hand → compare with the judge
python3 ewaluacja/kalibruj_sedziego.py --recznie recznie.jsonl
# agreement: 34/40 (85%)
# ⚠️ the judge MORE LENIENT in 5 of 6 disagreements
#    → on refusals: the judge accepts "I did not find it" when the answer WAS in the source
```

⭐ **The direction of the judge's error matters more than its size.** A lenient judge
inflates the score and **lulls you to sleep**. A strict judge deflates it and at most you
waste time on a problem that does not exist. If you have to choose — calibrate toward
strictness.

## 5. The regression gate

⭐ **This is the most important practical product of this part.** No change goes in
without a measurement.

```python
# $OSA/ewaluacja/bramka.py
PROGI = {
    "spadek_ogolny_pp":     2.0,    # a drop > 2 pp = rejection
    "spadek_kategorii_pp":  5.0,    # no category drops > 5 pp
    "min_odmowy":          90.0,    # ⭐ refusals must NEVER fall below this
    "wzrost_krokow":        1.3,    # the average number of steps does not grow by >30%
    "wzrost_tokenow":       1.5,
}

def bramka(nowy: dict, bazowy: dict) -> tuple[bool, list]:
    powody = []
    d = nowy["ogolem"] - bazowy["ogolem"]
    if d < -PROGI["spadek_ogolny_pp"]:
        powody.append(f"overall score {bazowy['ogolem']:.1f} → {nowy['ogolem']:.1f} ({d:+.1f} pp)")
    for k in bazowy["kategorie"]:
        dk = nowy["kategorie"][k] - bazowy["kategorie"][k]
        if dk < -PROGI["spadek_kategorii_pp"]:
            powody.append(f"category '{k}': {dk:+.1f} pp")
    if nowy["kategorie"].get("poprawna_odmowa", 100) < PROGI["min_odmowy"]:
        powody.append(f"⚠️ refusals {nowy['kategorie']['poprawna_odmowa']:.1f}% "
                      f"< {PROGI['min_odmowy']}% — the agent started guessing")
    if nowy["sr_krokow"] > bazowy["sr_krokow"] * PROGI["wzrost_krokow"]:
        powody.append(f"steps {bazowy['sr_krokow']:.1f} → {nowy['sr_krokow']:.1f}")
    return not powody, powody
```

**Hook it in at three places:**

```bash
# 1. before every commit that changes the prompt, the tools or the harness
python3 ewaluacja/bramka.py --przed-commitem

# 2. in the night task (part 11) — detects drift without your involvement
# 3. on every change of model or its version
```

## 6. What to learn from the big benchmarks

Do not run them. **Steal ideas from them.**

| Benchmark | An idea worth copying |
| :-- | :-- |
| **τ²-bench** | ⭐ **The user also calls tools.** Your set should have cases in which the state of the world changes **while** the agent is working |
| **SWE-bench** | ⭐ **Verification by the repository's tests** — a signal from execution, not from opinion |
| **GAIA** | Tasks requiring **many modalities and many steps**; evaluation against truth, not style |
| **Terminal-Bench** | Tasks in a real terminal — closest to what your agent does |

⭐ **τ²-bench is the most interesting one for you.** A classic golden set assumes the world
stands still. Your agent works in a world in which **you are adding files and changing the
calendar at the same time**. Add 3–5 such cases — they will be the hardest and the most
instructive.

## 10. Pitfalls of this part

| ID | Pitfall | Symptom | How to avoid |
| :-- | :-- | :-- | :-- |
| **P118** | **The agent evaluates itself** | Everything green, the user sees errors | External verification: execution → pattern → judge in isolation. Self-reflection **never as a gate** |
| **P119** | **No "correct refusal" category** | You optimize toward self-confidence; the agent always answers something | 20% of the set are questions with no answer in the data; a hard 90% threshold in the gate |
| **P120** | **One run per question** | The score jumps by 8 pp between measurements, you do not know why | ≥3 runs, report `pass^k` next to the average |
| **P121** | **An uncalibrated judge** | A lenient judge inflates and lulls; you think things are better | 40 cases by hand; record the error **direction**, calibrate toward strictness |
| **P122** | **A golden set generated by the model under test** | You measure repeatability, not correctness; 95% and useless | Questions from real logs and from failures. Every generated answer checked by hand |
